MCP Tool Security Checklist: Gating Money Moves in Model Context Protocol

MandateGuard - 2026 - Landing

Model Context Protocol (MCP) makes every capable model an automation platform in one install. That is exactly what makes it dangerous: a single MCP server exposes tools, and tools can move money. This checklist is the minimum bar for any MCP server that touches wallets, cards, or invoices in 2026.

1. Assume the model is compromised

Treat the LLM as an untrusted client. Whatever context it sends - a tool result, a webpage, an email - is attacker-influenced until proven otherwise. Design every payment tool as if the model will call it with the most adversarial arguments it can be tricked into constructing.

2. Enforce policy before the action, not after

A pre-action guard runs before the money moves and decides APPROVED or DENIED as a pure function of inputs. Post-action fraud detection is useful, but it cannot un-send a transfer. MandateGuard evaluates authorize() before execution - budgets, allowlists, rate limits, and mandate checks all run in that deterministic gate.

result = guard.authorize(
    actor="wallet-agent",
    tool="pay",
    params={"to": "0xSCAM", "amount": 5000},
)
# DENIED: destination 0xSCAM is denylisted

3. No LLM in the decision path

If the authorization itself goes through the model, the attack has already won: the attacker controls the context the model reasons from. The gate must be a deterministic engine - identical inputs, identical verdict, always. A prompt injection cannot change a policy rule.

4. Scoped spending with signed mandates

Give the agent a scope, not a card. An issuer signs an Ed25519 mandate (actor, tools, destinations, max amounts, expiry) and the guard verifies the signature on every call. The agent can only spend inside what was signed - there is no path to "just this once, trust me."

5. Budgets, rate limits, and denylists

Defense in depth, in order of cheapness:

  • Denylists first - known bad destinations fail fast
  • Allowlists - the agent may only reach pre-approved destinations
  • Per-call limits - no single call exceeds a ceiling
  • Per-window budgets - daily/hourly spend caps that reset deterministically
  • Rate limits - max calls per window, so a runaway loop exhausts policy before funds

6. Tamper-evident ledger

Every decision is appended to a SHA-256 chained ledger with a head hash. You can prove, after the fact, exactly what was approved, denied, and why - and detect any attempt to rewrite history. This is the audit trail your compliance team will ask for.

7. Ship it as an MCP server, gate it as middleware

Your wallet integration speaks to the MCP server; the server speaks to the guard; the guard speaks to policy. The LLM never gets a direct payment tool. MandateGuard ships this as an MCP server (stdio) with 14 tools and is published on the official MCP Registry as io.github.ezequiellich44-cmd/mandateguard.

Bottom line: if your agent can move money, the authorization step must be deterministic, scoped, and auditable - and it must never be part of the model's context. That is the entire job.
